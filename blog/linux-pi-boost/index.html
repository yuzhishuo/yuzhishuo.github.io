PI / boost：优先级继承与临时提权

优先级反转、PI 继承与 boost：带图说明 H/L/M 三人和锁链
📌
这篇讲一件事：高优先级的人等一把被低优先级拿着的锁时，内核怎么临时把优先级借给拿锁的人，免得被中间那档卡住。读完不需要对着源码。四个优先级字段见 。权重见 。
判断正在被抬高：生效优先级和自己的稳态优先级不一样。放锁之后两者重新相等。

1. 先问对问题：高的人为什么会一直等

三个角色，一把锁：

  • H 高：实时任务，FIFO 50。要进临界区。
  • L 低：普通任务，nice 0。已经拿着这把锁。
  • M 中：也不用这把锁，nice -5，比 L 更能抢 CPU。

没有优先级继承时，故事是这样的：L 进了临界区。H 来了，发现锁被占着，只能睡。M 不碰这把锁，却一直跑。L 被 M 挤掉，放不了锁。H 明明最高，反而要等 M 跑完。

这就叫 优先级反转：不是 H 直接输给 L，而是被中间那档间接堵住了。

图1 优先级反转：高的人反而一直等

可以把它想成：VIP 要进一间被清洁工占用的房间。走廊里一个实习生一直走来走去，清洁工插不进队，门就一直锁着。VIP 不是输给清洁工，是输给那个不关门、却占着路的人。

2. 办法：把高的优先级临时借给拿锁的人

协议叫 PI（Priority Inheritance，优先级继承）。做法很直白：谁拿着锁挡住了更高的人，就临时按那个更高的人来调度，好尽快做完临界区、放锁。

H 堵在 L 的锁上，就把 H 的生效优先级借给 L。L 暂时压过 M，跑完、放锁，H 才能进。借的是「此刻拿去选人的那个数」，不是把 L 改成实时任务。

图2 优先级继承：把 H 的优先级临时借给 L

两个词不要混：

PIboost
是什么协议：等锁的人把优先级借给拿锁的人动作：把借来的数写进生效优先级
什么时候发生有人堵在这把锁上拿锁的人生效优先级真的变了
什么时候结束锁被放开，或等锁的人走了de-boost：生效值掉回自己的稳态

用户态常见入口：pthread_mutex 设成 PTHREAD_PRIO_INHERIT。内核里对应的是带 PI 的 futex / rt_mutex。PREEMPT_RT 下，连不少自旋锁、普通 mutex 也会走这套。

3. 两本账：身份不动，生效值临时变小

一个任务身上同时挂着「我是谁」和「此刻调度器拿我当谁」。boost 只改后者。

图3 两本账：身份不动，生效值临时变小
字段稳态boost 期间
policy / nice / static_prio自己的不变
se.load（CFS 份额）由 nice 推出不变，也不走改权重那条路
normal_prio按 policy 算出来的稳态不变。这就是「没有人借给我时我该有的值」
prio通常等于 normal_prio变成借来的那个更小的数
sched_class跟 policy可以从 fair 临时切到 rt（甚至 dl）

生效优先级怎么算：

\text{L 的生效 prio} = \min(L.\mathrm{normal\_prio},\; H.\mathrm{prio})

内核轴上数字越小越高，所以 min 就是「取更高的那个」。多个人等同一把锁，只借最高的那一个。

怎么判断正在被抬高？prio 不等于 normal_prio。 左边是此刻拿去选人的值，右边是自己的稳态。

4. 一组具体数字走一遍

继续用上面三个人。记住：用户 FIFO 50 对应内核 prio = 99 - 50 = 49；nice 0 对应 120；nice -5 对应 115。

图5 一组具体数字：L 被抬到 49，再掉回 120

H 堵上之后：

L 的生效 prio = \min(120,\ 49) = 49

L 仍自称 SCHED_NORMAL、nice 仍是 0，但调度器已经把它从 CFS 队列挪到 RT 的 queue[49]。这段时间它跟真正的 FIFO 50 同一档抢 CPU，所以能压过 M。

L 放锁：没有人再借给它，pi_task 变成空，prio 掉回 120，调度类回到 fair。H 被唤醒，自己跑。M 这才有机会。

两个细节。

  1. 如果后来又有一个FIFO 80（内核 prio=19）也来等这把锁，L 会被再抬到 19。只看当前最高的等待者。
  2. fork 孩子时故意用 normal_prio，不把临时提权传给孩子。孩子出生时是「自己的稳态」，不是爸爸此刻借来的那个数。

5. 锁链：只抬挡你的人不够

更麻烦的情况：H 等 L 的锁 A，L 自己又堵在更低的人 Z 的锁 B 上。只把 L 抬高没有用——L 在睡，CPU 在 Z 手里。必须把 H 的优先级一路传到真正占着 CPU、拿着锁链末端的那个人。

图4 锁链：借优先级要一路传到真正拿着 CPU 的人

内核的走法可以记三步：

  1. H 堵在锁 A 上，把自己登记到「谁在等这把锁」。如果它是这把锁上最高的等待者，就写进 L 的「谁在等我」那棵树。
  2. 发现 L 自己也在等另一把锁，就顺着链往下走，把同样的高优先级再借给 Z。
  3. Z 被抬高 → 跑完放 B → L 醒、放 A → H 才能进临界区。

这就是 优先级继承链。顺带也能发现死锁：如果顺着走一圈又回到自己，说明锁互相等，返回死锁错误。链太长会被截断，避免无限走下去。

6. 什么时候借、什么时候还

可以按时间顺序记：

有人来等锁
  → 若他是这把锁上最高的等待者
  → 把拿锁的人抬到 min(自己稳态, 等待者 prio)
  → 拿锁的人若自己也在等锁，继续往下传

拿锁的人放锁
  → 唤醒最高的等待者
  → 拿锁的人身上「谁在等我」少了一个
  → 若没人再等，掉回自己的稳态（de-boost）
  → 若还有别人等，改借当前剩下的最高者

中间那档 M 全程不需要改：它没有拿这把锁，也没有等这把锁。PI 不抬无关的人。

空闲线程一般不会被抬。它关着中断、很快就会走完自己那小段，没有必要真去 boost idle。

7. 和 CFS 权重不要混

boost 不改 se.load，也不走 set_load_weight。原因很简单：L 并没有变成另一个 nice，它只是这段时间要按 RT 的规则插队。

改 nice被 PI boost
改的是身份：static_prio、normal_prio、se.load生效值：prio，可能换调度类
本核怎么选人仍在 CFS 里，份额变了切到 RT 后看队列下标，不看 vruntime
放锁 / 改回去nice 改回去，份额跟着改prio 掉回 normal_prio，再回 CFS，份额还是原来的

所以：一个被抬高的 nice 0 进程，看起来像 FIFO 50 在跑；临界区一结束，它立刻变回那个份额为 1024 的普通任务。负载跟踪（PELT）仍然按它真实跑了多久来记，跟这次临时提权是两件事。

8. 用户态什么时候会碰到

场景会不会走 PI
pthread_mutex 默认属性通常不会。普通 mutex 不继承优先级
pthread_mutexattr_setprotocol(PTHREAD_PRIO_INHERIT)会。走带 PI 的 futex
PTHREAD_PRIO_PROTECT（优先级天花板）另一套：拿锁时直接抬到预先设好的天花板，不是向等待者借
内核 rt_mutex；PREEMPT_RT 上的 spinlock / mutex会。这是内核里真正实现继承的那条路

实时线程和普通线程抢同一把用户态锁时，若没用 INHERIT，就会出现图 1 那种反转：实时线程干等，普通中优先级一直跑。

task_top_pi_waiter()（rtmutex_common.h:148）取 pi_waiters 最左节点，就是「谁在等我」里优先级最高的那个。

9.3 H 等锁：登记自己，必要时抬 L

调用点在 rt_mutex_slowlock 里拿不到锁之后（rtmutex.c:1722）。核心是 task_blocks_on_rt_mutex()：

/* rtmutex.c:1232 */
waiter->task = task;
waiter->lock = lock;
rt_mutex_enqueue(lock, waiter);     /* 挂到这把锁的等待树 */
task->pi_blocked_on = waiter;       /* H：我在等这把锁 */

/* :1265 只有自己是最高等待者，才去动 owner */
if (waiter == rt_mutex_top_waiter(lock)) {
	rt_mutex_enqueue_pi(owner, waiter);  /* 挂进 L->pi_waiters */
	rt_mutex_adjust_prio(lock, owner);   /* 抬 L */
	if (owner->pi_blocked_on)
		chain_walk = 1;                 /* L 自己还在等别的锁 → 图 4 */
}

rt_mutex_adjust_prio() 只做一件事：从 L 的 pi_waiters 里取出最高等待者，交给 rt_mutex_setprio。没人等了就传 NULL，等于 de-boost。

/* rtmutex.c:527 */
static void rt_mutex_adjust_prio(struct rt_mutex_base *lock,
                                 struct task_struct *p)
{
	struct task_struct *pi_task = NULL;

	if (task_has_pi_waiters(p))
		pi_task = task_top_pi_waiter(p)->task;

	rt_mutex_setprio(p, pi_task);   /* pi_task 就是 donor，图 2 里的 H */
}

9.4 真正改数：rt_mutex_setprio

注释写得很直：改 effective priority，不碰 ->normal_prio。对应第 3 节那两本账。

/* core.c:7481 */
void rt_mutex_setprio(struct task_struct *p, struct task_struct *pi_task)
{
	prio = __rt_effective_prio(pi_task, p->normal_prio);
	/* sched.h:4128：有 donor 就 min(自己稳态, donor->prio) */

	p->pi_top_task = pi_task;     /* 记下借给我的人 */
	next_class = __setscheduler_class(p->policy, prio);
	/* policy 仍是 SCHED_NORMAL，但 prio=49 时 next_class 变成 rt */

	p->sched_class = next_class;
	p->prio = prio;               /* 只写生效值 */
}

__setscheduler_class 看的是 prio 数字，不是 policy。所以 L 的身份还是 NORMAL，人已经被挂到 RT 的 queue[49]。这就是图 3 右边那一栏。

idle 一般不抬（core.c:7540），对上第 6 节。

9.5 L 放锁：先 de-boost，再唤醒 H

顺序很重要，注释也强调了：必须先从 pi_waiters 摘掉 H、把 L 掉回去，再唤醒 H。否则会短暂出现两个人顶着「同一档」优先级。

/* rtmutex.c:1411 rt_mutex_slowunlock */
/* 没人等：直接把 owner 清掉就走 */
/* 还有人等： */
mark_wakeup_next_waiter(&wqh, lock);   /* :1466 */

/* mark_wakeup_next_waiter :1312 */
rt_mutex_dequeue_pi(current, waiter);  /* L->pi_waiters 去掉 H */
rt_mutex_adjust_prio(lock, current);   /* 没人借了 → setprio(L, NULL) → 掉回 120 */
rt_mutex_wake_q_add(wqh, waiter);      /* 这才唤醒 H */

H 被唤醒后再次 try_to_take_rt_mutex（rtmutex.c:1175）：清掉自己的 pi_blocked_on，若锁上还有别人等，把新的最高等待者挂到 新 owner（H） 的 pi_waiters。继承关系转到下一个人身上。

等锁失败退出走 remove_waiter()（:1541）：同样只在自己曾是最高等待者时，才重新 adjust_prio owner。

9.6 fork 不传 boost

/* core.c:4822 */
/* Make sure we do not leak PI boosting priority to the child. */
p->prio = current->normal_prio;

故意不用 current->prio。对上第 4 节第 2 个细节。

9.7 回头怎么翻

  1. 先在 rtmutex.c 搜 task_blocks_on_rt_mutex，顺着 :1266 看到 adjust_prio。
  2. 跳到 rt_mutex_setprio，确认它只写 prio / sched_class / pi_top_task。
  3. 放锁搜 mark_wakeup_next_waiter，看「先 deboost 再 wake」那两行。
  4. 锁链搜 rt_mutex_adjust_prio_chain（:678），对应图 4。
  5. 用 p->prio != p->normal_prio 判断正在被 boost（rt.c 里也是这么认 RT-boosted）。

小结

反转：H 等锁，L 拿锁，M 抢 CPU  →  H 一直醒不了
PI：把 H 的 prio 借给 L  →  L 压过 M、放锁  →  H 才能跑
boost：只改 prio（和调度类），不改 nice / normal_prio / se.load
判断：prio != normal_prio
放锁：de-boost，掉回自己的稳态
fork：孩子拿 normal_prio，不继承这次临时提权
代码：blocks_on → adjust_prio → setprio；放锁 mark_wakeup_next_waiter 先 deboost 再 wake

记住清洁工和 VIP 就够用了：门在清洁工手里时，先让清洁工按 VIP 的待遇把走廊走完；门一开，清洁工还是清洁工。翻代码从第 9 节那张对照表进。
